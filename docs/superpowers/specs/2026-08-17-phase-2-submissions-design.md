# Writers Circle Phase 2 投稿系统设计

## 目标

Phase 2 为 Writers Circle 增加一个适合手机使用的公开投稿页面，以及一套只供管理员使用的投稿审核后台。

投稿人无需注册账号，打开 `/submit` 后即可粘贴文章并投稿。稿件进入 Payload CMS 后，由管理员人工查看和修改审核状态。整个流程坚持“投稿与审核分开、稿件默认不公开、任何内容不得自动发布”的原则。

本阶段不开发附件上传、投稿查询、通知、AI、新闻搜索、公开作品展示、微信公众号接口或自动发布功能。

## 已确认的方案

在以下三种方式中，采用第一种：

1. 公开投稿页，无需登录。操作最简单，适合成员从手机进入。
2. 共享投稿密码。虽然多一道保护，但密码容易遗忘或转发。
3. 每位成员单独登录。身份识别更准确，但使用和维护成本明显更高。

公开投稿页将配合字段白名单、长度限制、重复提交防护、隐藏反垃圾字段和访问频率限制，降低误用风险。正式上线后如果实际垃圾投稿较多，再单独评估验证码或邀请机制，不在 Phase 2 提前实现。

## 投稿页面

### 页面地址

- 本地开发：`http://localhost:3000/submit`
- 正式上线：沿用同一路径 `/submit`，以后由真实域名承载。

公众号接入不属于本阶段。未来正式上线后，公众号菜单可以直接指向该页面，不需要在微信内重新开发一套表单。

### 投稿字段

- `submitterName`：投稿人姓名，必填。
- `penName`：笔名，选填。
- `contact`：联系方式，必填，可填写手机号或微信号。
- `title`：文章标题，必填。
- `category`：作品类别，必填，可选“诗歌”“小说”“散文”“评论”“其他”。
- `content`：文章正文，必填，以纯文本方式提交和保存。
- `notes`：补充说明，选填。
- `rightsConfirmed`：原创或授权确认，必须勾选后才能提交。

页面不得要求投稿人填写残疾类别、残疾等级、身份证号、残疾人证号码或其他与投稿无关的敏感信息。

### 投稿反馈

提交成功后显示由服务器生成的投稿编号。编号用于管理员与投稿人联系核对，不公开稿件数量，也不允许通过编号直接读取稿件。

页面不提供投稿进度查询。需要退回修改时，管理员在后台记录状态，再通过投稿人填写的联系方式人工联系；投稿人修改后可以重新投稿，并在补充说明中填写原投稿编号。

## 后台投稿管理

新增 Payload 集合 `submissions`，后台中文名称为“投稿管理”。集合只允许已登录管理员读取、创建、修改和删除。

除公开投稿字段外，后台保存以下管理字段：

- `submissionNumber`：服务器生成且唯一的投稿编号。
- `relatedMember`：选填，管理员可将稿件关联到现有成员档案。公开投稿页不显示成员名单，也不允许投稿人自行建立关联。
- `status`：审核状态，默认“待审核”。
- `reviewNotes`：内部审核意见，仅管理员可见。
- `submittedAt`：投稿时间，由服务器记录。

审核状态固定为：

- `submitted`：待审核。
- `reviewing`：审核中。
- `revisionRequested`：退回修改。
- `accepted`：已采用。
- `rejected`：不采用。

后台列表默认显示投稿编号、标题、投稿人、作品类别、审核状态和投稿时间，并允许按状态和时间查找稿件。Phase 2 不制作自定义编辑工作台，继续使用 Payload 自带后台，降低长期维护成本。

## 数据流与权限边界

投稿采用独立的公开提交入口，不直接开放 Payload 集合的公开新增权限。

处理流程如下：

1. 投稿人在 `/submit` 填写表单。
2. 浏览器把允许公开填写的字段发送到专用服务器入口。
3. 服务器只接收字段白名单中的内容，并重新验证必填项、长度、类别和授权确认。
4. 服务器生成投稿编号和投稿时间，并以内部方式写入 Payload。
5. 浏览器只收到成功状态和投稿编号，不收到数据库记录、联系方式、审核意见或其他稿件信息。
6. 管理员登录 `/admin` 后在“投稿管理”中审核。

未登录用户不得通过 Payload REST 或 GraphQL 接口读取、修改或删除任何投稿，也不得设置审核状态、关联成员或写入内部审核意见。

## 隐私与安全

- 投稿内容、联系方式、成员关联和审核意见默认全部为后台私有数据。
- 公开页面不显示32位成员名单，不读取成员档案，也不输出任何残疾信息。
- 服务端只接受明确允许的投稿字段，忽略或拒绝额外后台字段。
- 正文按纯文本处理，不接受投稿人提供的 HTML 或脚本。
- 姓名、联系方式、标题、正文和说明设置合理长度上限，避免异常大请求。
- 页面加入隐藏反垃圾字段；正常用户看不到也无需操作。
- 同一来源短时间内频繁投稿时返回清楚提示，限制规则保持简单，便于以后调整。
- 提交按钮在请求期间不可重复点击，并通过一次性请求标识降低网络重试产生重复稿件的可能。
- 验证失败、访问过于频繁或数据库异常时，不得显示投稿成功或生成虚假编号。
- 不在代码、日志、Git 提交或浏览器错误信息中暴露密码、Secret、完整联系方式或正文。

Phase 2 的本地限流服务于开发和首版单机部署。未来改变为多台服务器时，应重新评估共享限流存储；本阶段不提前增加 Redis 等额外服务。

## 手机与无障碍设计

投稿页面以手机使用为主，同时保证桌面浏览器可用：

- 使用清楚的中文标签和简短说明，不依赖技术术语。
- 输入框与按钮尺寸适合触屏操作。
- 保持足够的文字和颜色对比度。
- 每个输入项都使用明确标签，不只依赖占位提示文字。
- 支持键盘完成全部操作，并保持清楚的焦点提示。
- 错误信息显示在对应字段附近，同时让读屏软件能够识别。
- 不使用拖拽、复杂富文本编辑器或仅靠颜色表达状态的设计。
- 正文输入区域支持较长文本，并保留投稿人输入的自然分段。

## 错误处理

- 必填内容缺失时，在对应字段显示通俗中文提示，并保留用户已经填写的其他内容。
- 作品类别不在允许范围内、正文过短或字段超长时，服务器拒绝保存。
- 未勾选原创或授权确认时，不允许提交。
- 触发频率限制时，提示稍后再试，不显示内部技术信息。
- 数据库写入失败时保留页面内容并提示投稿尚未成功。
- 网络中断或重复点击不得静默生成多份难以辨认的稿件。
- 后台记录不存在或已被删除时，管理员应看到正常的未找到提示，不造成其他稿件损坏。

## 测试与验收

自动化和运行时验收至少覆盖：

- 投稿集合已经注册，后台字段和默认状态符合设计。
- 未登录用户不能通过 Payload 接口读取、修改或删除投稿。
- 公开提交入口只接受允许字段，不能写入审核状态、审核意见或成员关联。
- 必填、类别、长度和原创或授权确认验证生效。
- 投稿编号由服务器生成且保持唯一。
- 隐藏反垃圾字段、访问频率限制和重复提交防护生效。
- 投稿成功后页面只显示投稿编号，不泄露稿件数据。
- 手机尺寸、键盘操作、字段标签和错误提示符合无障碍要求。
- 已登录管理员可以查看虚构测试稿件、修改状态、填写审核意见并关联虚构成员。
- 首页和 Payload 后台继续正常打开。
- 单元测试、代码检查、类型生成和生产构建全部通过。

运行时验收只使用完全虚构的姓名、联系方式和文章内容。验证完成后删除虚构稿件，确保数据库中没有被误认为真实投稿的数据。

## 本阶段明确不做

- Word、PDF、图片、音频或其他附件上传。
- 投稿人账号、登录、找回密码或成员身份验证。
- 投稿进度查询、稿件修改链接或投稿人个人中心。
- 短信、邮件、微信模板消息或其他自动通知。
- AI改稿、摘要、分类、评分、排版或自动审核。
- 新闻搜索、新闻候选、线索提交或网页采集。
- 公开作品列表、作品详情页或成员展示页。
- 微信公众号 AppID、AppSecret、菜单接口、草稿箱接口或自动发布。
- Docker Compose、正式域名、服务器和线上部署。

## 完成条件

Phase 2 只有在以下条件全部满足后才能完成：

- `/submit` 可以在手机和桌面浏览器正常投稿。
- 稿件安全进入 Payload 的“投稿管理”，默认状态为“待审核”。
- 管理员可以完成查看、关联成员、修改状态和填写审核意见。
- 所有公开与后台权限边界符合本设计。
- 虚构稿件完成一次实际投稿与审核流程，并在验收后删除。
- 测试、代码检查、类型生成和生产构建通过。
- 首页和后台通过实际 HTTP 检查。
- 没有真实密码、Secret、成员隐私或真实投稿进入 Git。
- 主要使用方法写入中文文档。

完成后停止，不进入新闻搜索、AI、微信公众号接入、公开展示或任何其他后续阶段。
