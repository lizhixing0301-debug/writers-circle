# Writers Circle Phase 1 成员档案设计

## 目标

Phase 1 为 Writers Circle 建立便于非程序员维护的“成员档案”后台，用于保存三十二位成员的文学资料，并为后续投稿、新闻搜索和成员展示提供稳定的数据基础。

本阶段只开发 Payload CMS 后台中的成员管理能力。公开成员页面、公开数据接口、投稿、新闻搜索、AI、微信公众号、批量导入和其他业务功能均不在本阶段范围内。

## 已确认的原则

- 项目继续采用单体 Next.js、Payload CMS 和 PostgreSQL 结构。
- 后台资料与未来公开资料严格分开；建立档案不代表允许公开。
- 残疾类别和残疾等级需要保留信息位，但属于敏感信息，默认仅后台可见。
- 不收集身份证号、残疾人证号码或其他本阶段不需要的证件信息。
- 未来制作成员展示页面时，只能读取已获授权且明确允许公开的字段。
- Phase 1 使用一条完全虚构的测试资料进行验收，不录入真实成员信息。

## 实现方式

采用“成员档案 + 图片资源”两个 Payload 集合：

1. `members`：保存成员主档案、作品、授权状态、公开控制和内部资料。
2. `media`：保存头像等图片文件及必要的替代文字。

代表作品作为成员档案内的可重复结构化列表保存，不单独建立作品集合。这个方案比把所有内容塞进一个集合更清楚，也比拆成成员、作品、授权记录等多个集合更易维护，符合目前三十二人规模和非程序员长期维护的要求。

## 成员档案结构

### 基本身份

- `name`：姓名，必填。
- `penName`：笔名，选填。
- `aliases`：其他署名，可填写多项。
- `slug`：未来成员页面的网址标识，必填且唯一。
- `status`：成员状态，取值为“在册”“暂停”“归档”，默认“在册”。归档只隐藏或停用资料，不删除数据。

### 文学资料

- `region`：所在地区。
- `literaryIdentities`：文学身份，可填写作家、诗人、评论家等多项内容。
- `organizations`：所属机构，可填写多项。
- `biography`：后台完整简介。
- `publicBiography`：为未来展示页准备的公开简介；当前不会自动公开。
- `representativeWorks`：代表作品列表。每项包含作品名、作品类型、出版或发表年份和备注。

### 后续搜索资料

- `searchKeywords`：以后用于新闻搜索的关键词组合，可填写多项。
- `websites`：个人网站或公开主页，可填写多项名称和网址。
- `knownWeChatAccounts`：已知公众号名称或说明，仅作为后台资料。
- `internalNotes`：内部备注，任何未来公开页面均不得读取。

### 图片和展示预留

- `profileImage`：关联图片资源中的头像。
- `displayOrder`：未来展示列表的排序数字。
- `publicProfileEnabled`：是否允许未来展示个人主页，默认关闭。

Phase 1 不制作公开成员列表或详情页，但保留以上字段，使以后增加展示页面时无需重构成员数据。

## 残疾信息与公开授权

### 残疾信息

- `disabilityCategory`：残疾类别，取值为“肢体”“视力”“听力”“言语”“智力”“精神”“多重”“其他”“未提供”。
- `disabilityLevel`：残疾等级，取值为“一级”“二级”“三级”“四级”“未提供”。

两项信息默认仅后台管理员可见，不得因为个人主页开启而自动公开。

### 授权记录

- `consentStatus`：取值为“未征求”“已同意”“不同意”，默认“未征求”。
- `consentDate`：记录获得意见或授权的日期。
- `consentNotes`：记录授权范围或其他说明。
- `showDisabilityCategory`：是否允许未来公开残疾类别，默认关闭。
- `showDisabilityLevel`：是否允许未来公开残疾等级，默认关闭。

系统必须阻止以下不一致状态：

- `consentStatus` 不是“已同意”时，不能开启个人主页公开。
- `consentStatus` 不是“已同意”时，不能开启残疾类别或等级的公开开关。
- 授权状态从“已同意”改为其他状态时，所有公开开关必须自动关闭，或拒绝保存并给出清楚提示。实现时选择对非程序员更易理解、测试更稳定的方式，并在实施计划中明确。

这些开关只是为未来展示准备。Phase 1 没有公开页面，也没有公开输出敏感信息的接口。

## 图片资源

`media` 集合只承担成员头像等图片文件管理，至少包含：

- 上传文件。
- 图片替代文字，便于无障碍阅读，必填。
- 内部说明，选填。

允许的文件类型以常用网页图片为主，并设置合理的文件大小限制。具体类型和限制在实施计划中依据 Payload 当前版本的官方能力确定，避免加入复杂的图片处理服务。

图片资源不得用于上传身份证、残疾人证、授权书扫描件或其他敏感证明材料。头像应按未来可能公开的图片管理；即使当前集合只允许管理员读取，也不能把文件访问控制当作敏感证件的唯一保护措施。

## 权限与数据接口

- `members` 和 `media` 的新增、读取、修改、删除仅允许已登录的 Payload 管理员。
- Payload 自动生成的 REST/GraphQL 能力仍保留，但未登录用户不得通过这些接口读取成员档案或图片资料。
- Phase 1 不创建公共成员 API。
- 未来展示页面需要单独建立“安全公开数据层”，只返回 `publicProfileEnabled` 已开启且逐项允许公开的字段。
- `internalNotes`、`consentNotes` 以及未获得公开授权的残疾信息永远不能进入未来公开数据结果。

这使数据结构提前支持未来展示，同时避免当前阶段为了所谓“预留接口”而过早开放真实数据。

## 后台使用流程

1. 管理员登录 `/admin`。
2. 打开“成员档案”。
3. 新建或编辑成员资料。
4. 如需头像，先在“图片资源”上传图片并填写替代文字，再在成员档案中选择该图片。
5. 保存时由 Payload 验证必填字段、唯一网址标识和授权规则。
6. 归档成员时只改变状态，不删除历史资料。

后台字段应按“基本身份、文学资料、搜索资料、展示预留、残疾信息、授权记录、内部备注”分组，字段标签和说明使用中文，降低维护难度。

## 测试资料

验收时创建一条明显标注为虚构的“测试成员”资料。测试资料不得使用真实人物姓名、联系方式或隐私信息。

验证完成后可以删除该资料。是否保留测试资料不影响 Phase 1 功能，但正式录入三十二人资料前应确保测试资料不会被误认为真实成员。

## 错误处理

- 姓名或网址标识缺失时，后台应显示明确的中文字段错误。
- 网址标识重复时，应阻止保存。
- 授权不足却开启公开选项时，应阻止或自动纠正，并给出管理员能够理解的反馈。
- 图片类型或大小不符合要求时，应显示上传错误，不得造成成员档案损坏。
- 数据库或服务异常时，不得把未保存的数据描述为保存成功。

## 测试与验收

自动化和运行时验收至少覆盖：

- 成员集合和图片集合已正确注册。
- 姓名、网址标识等必填和唯一性规则生效。
- 成员、授权和残疾公开开关的默认值符合设计。
- 未获得同意时不能开启任何公开选项。
- 未登录请求不能读取成员和图片集合数据。
- 已登录管理员可以新增、读取和编辑虚构测试成员。
- 后台 `/admin` 正常打开。
- 现有首页继续正常打开。
- 单元测试、代码检查、类型生成和生产构建全部通过。

## 完成条件

Phase 1 只有在以下条件全部满足后才能完成：

- `members` 与 `media` 集合已经实现并接入 Payload。
- 字段、默认值、授权规则和管理员权限符合本设计。
- 虚构测试成员的新增、编辑和保存已经实际验证。
- 测试、代码检查、类型生成和生产构建通过。
- 首页和后台通过实际 HTTP 检查。
- 没有真实密码、Secret 或真实成员隐私进入 Git。
- 主要使用方法已写入中文文档。

完成后停止，不进入投稿、新闻搜索、AI、微信公众号、公开成员展示或任何其他后续阶段。
